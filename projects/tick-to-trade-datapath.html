10GbE FPGA
Tick-to-Trade Datapath

A SystemVerilog hardware and software system that takes market-data packets off a 10G network path, parses them, updates book state, runs fixed-point decision and risk logic, emits simulated order messages, and proves latency and timing on real hardware.

Stack
SystemVerilog, Python, cocotb, C++20
Target hardware
Kria KR260, SFP+ 10G
Method
Simulation-first, then hardware bring-up
Status
Active development

Status. This project is in active development. Timing has not been closed, nothing has run on hardware, no latency has been measured, and nothing is connected to any live or production trading system. Everything under Evidence and Acceptance criteria below is a target, written down so the goalposts cannot move.

Why this workload

Market data is one of the most demanding latency targets available to study, which makes it a useful forcing function. The engineering problems underneath are general: parse a protocol at line rate, keep a pipeline from stalling unpredictably, do arithmetic in fixed point inside fabric, and enforce an interlock that software cannot override. The same problems appear in radar and avionics front ends, robotics, industrial control, and network equipment.

Scope discipline

The plan is deliberately narrow. No reinforcement learning, no full exchange protocol coverage, and no TCP stack. Each of those would widen the surface area faster than it could be verified, and an unfocused system is easier to dismiss than a small one that is measured end to end. The target is a clean, verified, hardware-tested networking datapath.

The datapath

Every stage in the critical path is original RTL rather than assembled IP. That is the point of the exercise — the interesting decisions live in the parser and the pipeline, not in the wiring.

  • 10G ingress. SFP+ path into a MAC and streaming interface.
  • UDP/IP parse. Header strip, filtering, checksum, framing.
  • Market-data decode. Message framing and field extraction.
  • Book state. Per-symbol tracking with deterministic top-of-book updates.
  • Decision logic. Fixed-point evaluation in the datapath.
  • Risk gate. Hardware-enforced checks that no order may bypass.
  • Order encode. Message build and TX egress.
  • Latency counters. Cycle stamps at each stage boundary, for accounting rather than estimation.

Target hardware

A Kria KR260 is the intended board: it carries an SFP+ cage alongside four RJ45 ports at a price that makes a personal project realistic. Alveo-class cards are closer to production trading hardware and correspondingly far more expensive; the engineering being demonstrated does not depend on the price of the board.

Verification

Python and cocotb drive the environment, and the failure cases matter more than the happy path:

  • Randomized packet streams compared against a Python golden model.
  • Malformed packets, truncated frames, and bad checksums.
  • Sequence gaps, so recovery behaviour is defined rather than discovered.
  • Reset behaviour mid-stream.
  • Back-pressure, so a stalled downstream cannot corrupt book state.

Host tooling

C++20 software on the host side: packet replay, control register access, risk parameter configuration, structured logging, and a simulated exchange and order sink so the egress path has somewhere to land.

Evidence

Artifacts the project is working toward, none of them yet produced:

  • Synthesis and implementation timing reports at the target clock.
  • Resource utilisation reports.
  • Waveform captures from simulation, and ILA captures from hardware.
  • Packet-to-decision latency in both cycles and nanoseconds.
  • A technical write-up covering architecture, the latency breakdown, verification strategy, limitations, and next steps.

Acceptance criteria

The project is finished when every line below can be stated as fact. Until then they are open items.

  • Closes timing at the target clock frequency.
  • Runs on real FPGA hardware.
  • Parses market-data-style UDP packets.
  • Maintains deterministic book and top-of-book state.
  • Enforces hardware risk checks that cannot be bypassed.
  • Verified with randomized cocotb tests against a Python golden model.
  • Controlled and replayed from C++ host software.
  • Packet-to-decision latency measured in cycles and nanoseconds.
  • Timing, resource, and latency tradeoffs documented in a technical report.

References

Latency claims should be measured against published baselines rather than asserted, so these are the references the work is being checked against:

  • AMD PG210 — 10G/25G Ethernet latency, for MAC and PCS latency figures.
  • Kria KR260 specifications, for the SFP+ and Ethernet interfaces.
  • Corundum application block, for low-latency streaming and AXI-Lite control patterns around custom logic.
